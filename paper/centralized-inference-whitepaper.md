# FactoryGuard 集中推理架构论证报告

**副标题：面向中小微制造企业的低成本、可运维视频智能方案**

版本：v1.0
日期：2026-10-20
适用对象：项目决策人、技术评审专家、甲方信息化/安全负责人

---

## 0. 文档定位与结论

本报告回答三个问题：

1. FactoryGuard 为什么应优先采用集中推理，而不是每台值守终端各自推理？
2. 集中推理为什么在中小微工厂场景中总拥有成本更低？
3. 这种架构为什么更容易部署、运维、审计和扩展？

**结论：** 对 4～32 路摄像机、单一厂区/园区、已有 NVR 和局域网的中小微制造企业，集中推理通常比终端推理更适合。其优势不是单纯“中心机器性能更强”，而是把模型、算力、事件库、规则、通知、备份、审计和升级收敛到一套可管理的基础设施中，使终端变薄、重复建设减少、故障面收敛、算力可以共享。

需要强调：集中推理不是所有场景的绝对正确答案。摄像机跨广域分布、视频禁止出园区、网络不稳定或需要毫秒级本地联动时，应保留边缘推理或采用边缘-中心混合架构。本报告在第 11 节明确给出适用边界。

本报告中的证据分为三类：

- **[标准]**：国家标准、国际标准或官方法规；
- **[论文]**：同行评议论文或公开预印本，给出 DOI/arXiv 编号；
- **[工程假设]**：用于预算和方案设计的工程估算，必须通过现场 PoC 校准，不能当作厂商承诺。

## 1. 项目边界与关键前提

### 1.1 目标场景

FactoryGuard 主要面向以下客户：

- 单个工厂、园区或仓储区域；
- 4～32 路摄像机，已有 NVR；
- 摄像机与中心主机处于同一局域网或可管控的企业网络；
- 需要人员入侵、区域滞留、越线、PPE 等安全告警；
- 值守人员少，通常 1～3 个值班点；
- 没有专职 AI 团队，IT 运维能力有限；
- 希望一次性采购、本地部署，不愿意承担持续云服务费用。

### 1.2 关键工程假设

- NVR 继续负责 7×24 主码流录像；
- 智能分析使用低分辨率、低帧率子码流，建议 480p～720p、2～5 FPS；
- 事件截图和事件前后短视频由中心保存；
- 中心主机运行模型、规则、事件库、通知 Outbox 和审计；
- 值守终端只负责显示、确认、回放和配置操作；
- 中心主机和终端位于同一受控局域网，网络时延通常在数十毫秒以内。

以上假设如果被现场条件推翻，应在方案阶段重新测算。

## 2. 两种架构的定义

### 2.1 终端推理

每台值守终端分别完成：

```text
RTSP 取流 → 本地模型推理 → 规则判断 → 本地事件库 → 本地通知
```

每台终端都是一套完整的“小系统”，需要独立安装模型、推理运行时、数据库和通知配置。

### 2.2 集中推理

中心主机完成：

```text
RTSP 取流 → 中心模型推理 → 规则判断 → 中心事件库 → 中心通知
```

值守终端只完成：

```text
登录 → 实时预览 → 事件确认/误报 → 回放 → 配置/审计
```

### 2.3 推荐目标架构

```text
摄像机 / NVR
   │
   ├── 主码流：NVR 7×24 录像、事后取证
   └── 子码流：低分辨率、低帧率分析流
                    │
          ┌─────────▼──────────┐
          │ 中心推理主机        │
          │ YOLO + 规则引擎     │
          │ 事件库 + Outbox     │
          │ Webhook/邮件/短信   │
          └─────────┬──────────┘
                    │
        ┌───────────┴───────────┐
        │                       │
   值守终端 A               值守终端 B
   只显示/确认/回放         只显示/确认/回放
```

**工程建议：** 第一阶段可先实现“终端取流、中心推理”，验证模型、网络和告警闭环；第二阶段再演进为“中心直接拉取 RTSP 子码流”，进一步减少终端参与和重复取流。

## 3. 为什么终端推理不适合本项目的主要客户

终端推理在少数单机、单摄像头场景中可以工作，但它与 FactoryGuard 的目标客户和产品定位存在结构性冲突。

### 3.1 硬件重复采购

每台需要推理的终端都必须具备足够的 CPU/GPU、内存、散热和稳定供电。摄像机数量不变时，增加值守点就意味着重复购买推理硬件。

### 3.2 算力无法共享

不同摄像头、不同时段的负载并不均衡。终端推理无法把 A 终端的空闲算力转移给 B 终端；中心推理可以通过任务队列、批处理和优先级调度共享同一套算力。

### 3.3 模型和依赖版本漂移

终端数量越多，模型文件、ONNX Runtime 版本、Python 依赖、驱动和配置越容易不一致。最终会出现“同一规则在不同终端结果不同”的问题。

### 3.4 事件库分裂

每台终端各自保存 SQLite、截图、片段和审计记录，导致：

- 事件无法统一检索；
- 跨摄像头关联困难；
- 备份和迁移复杂；
- 甲方难以获得一份完整的事件台账。

### 3.5 通知重复或遗漏

多个终端可能对同一事件重复发送 Webhook、邮件或短信，也可能因为通道配置不同而出现遗漏。中心化 Outbox 更适合统一去重、重试、熔断和审计。

### 3.6 运维成本被低估

终端推理的真实成本不仅是电脑采购价，还包括：

- 每台终端的安装和升级；
- 每台终端的模型/驱动排障；
- 每台终端的日志、备份和磁盘清理；
- 每台终端的凭据和通道配置；
- 每次规则调整的重复操作。

对没有专职 AI 运维人员的小微企业，这些隐性成本通常高于一台中心主机。

## 4. 集中推理为什么在技术上更适合 FactoryGuard

### 4.1 算力池化，提高利用率

中心推理可以把多路视频请求放入统一任务队列，根据区域重要程度分配帧率：

- 危险区域：5～10 FPS；
- 一般区域：2～5 FPS；
- 无人时段：1～2 FPS；
- 事件触发后：短时提高检测频率。

这种动态调度在终端推理中很难实现。

### 4.2 模型、规则和阈值统一

中心只维护一份模型和一套规则，天然保证：

- 所有摄像头使用同一模型版本；
- 所有终端看到同一告警口径；
- 规则修改一次即可全局生效；
- 模型回滚、灰度和 A/B 测试更容易。

### 4.3 跨摄像头协同更容易

中心拥有全局事件和时间线，便于实现：

- 同一人员在多个摄像头之间的轨迹关联；
- 跨镜头重复告警合并；
- 产线级、区域级事件聚合；
- 统一优先级和值班分派。

如果每台终端独立推理，跨摄像头能力仍需额外建设中心聚合层，架构反而更复杂。

### 4.4 终端变薄，部署更接近“ appliance ”

中心推理可以把产品做成一台可交付的中心设备：

- 接上局域网；
- 配置 NVR/摄像机；
- 启动中心服务；
- 其他电脑打开控制台即可使用。

终端不需要安装模型和推理运行时，也不需要独立 GPU。这更符合小微企业“买来就能用”的预期。

### 4.5 可观测性和故障定位更好

中心可以统一采集：

- 每路视频在线状态；
- 推理延迟和队列积压；
- CPU/GPU/内存占用；
- 模型版本和健康状态；
- 通知成功率和重试次数；
- 磁盘容量、数据库完整性和审计日志。

这比逐台终端排查更容易形成可交付的运维能力。

## 5. 成本模型：为什么总拥有成本更低

### 5.1 总拥有成本公式

```text
TCO = 推理硬件 + 终端设备 + 网络与存储 + 部署工时
      + 年度运维 + 模型升级 + 故障停机损失
```

终端推理和集中推理的差异不在某一项硬件，而在重复项的数量。

### 5.2 符号化比较

设：

- `N`：需要推理的终端数量；
- `C_edge`：单台可推理终端的硬件与部署成本；
- `C_center`：一台中心推理主机的硬件与部署成本；
- `C_model`：一套模型/依赖/配置的部署成本；
- `C_ops`：每套系统的年度运维成本；
- `C_db`：每套事件库的备份与治理成本。

终端推理的近似成本：

```text
TCO_edge ≈ N × (C_edge + C_model + C_ops + C_db)
```

集中推理的近似成本：

```text
TCO_center ≈ C_center + C_model + C_ops + C_db + N × C_thin_client
```

当 `C_thin_client` 接近 0（复用已有办公电脑）时，只要 `N ≥ 2` 且终端原本需要升级推理硬件，集中推理通常就具备成本优势。

### 5.3 8 路摄像机、3 个值守点的示例

以下仅为预算级工程估算，不是供应商报价，实际价格必须按当地采购和现场条件核定。

| 成本项 | 终端推理方案 | 集中推理方案 |
|---|---|---|
| 推理硬件 | 3 台可推理电脑 | 1 台中心主机 |
| 模型/运行时 | 3 套 | 1 套 |
| 事件数据库 | 3 个 | 1 个 |
| 通知配置 | 3 套 | 1 套 |
| 升级操作 | 3 次 | 1 次 |
| 备份操作 | 3 次 | 1 次 |
| 值守终端 | 仍需显示设备 | 可复用办公电脑/瘦客户端 |
| 新增摄像头 | 可能要升级某台终端 | 在中心主机扩容或加节点 |

规划级硬件区间可参考：

- **CPU 中心主机**：8 核以上、16 GB 内存、SSD，适合约 4～8 路低帧率分析；
- **GPU 中心主机**：消费级/专业级 GPU、32 GB 内存、1 TB SSD，适合约 16～32 路，具体取决于模型、分辨率和帧率；
- **UPS、交换机和机柜**：按现场供电和网络条件配置；
- **终端**：优先复用现有办公电脑，避免重复采购。

为了便于甲方做首轮预算，下面给出一个**仅供立项、不是报价**的规划区间。实际价格必须以当地采购、品牌、供货周期和施工条件为准。

| 项目 | 规划假设 | 说明 |
|---|---:|---|
| 可推理终端（每台） | 6,000～12,000 元 | 含可运行模型的 CPU/GPU、内存和基础部署 |
| CPU 中心主机 | 4,000～8,000 元 | 约 4～8 路低帧率分析，不含 UPS/机柜 |
| GPU 中心主机 | 12,000～25,000 元 | 约 16～32 路，具体取决于模型和帧率 |
| 瘦客户端（新增时） | 0～3,000 元/台 | 优先复用现有办公电脑，增量为 0 |
| UPS、交换机和机柜 | 1,000～3,000 元 | 按现场条件配置 |

以“8 路摄像机、3 个值守点”为例：

- 终端推理：3 台可推理终端约 18,000～36,000 元，外加 3 套模型、数据库和运维配置；
- 集中推理：1 台 CPU/GPU 中心主机加网络配套约 7,000～28,000 元，终端复用现有电脑时不再采购推理硬件。

这个区间足以说明集中推理在小微场景中的成本逻辑，但不能替代正式报价和 PoC 测算。

### 5.4 成本敏感性

集中推理并非在任何规模下都更便宜：

- 1 台终端、1～2 路摄像机：终端推理可能更简单；
- 2～3 个值守点且需要独立推理：集中推理通常更经济；
- 4 路以上且需要统一事件库/通知：集中推理优势明显；
- 16 路以上：中心 GPU 或推理节点扩容通常比逐台升级终端更可控；
- 多个远距离厂区：应考虑“园区中心 + 边缘节点”的混合架构，而不是强行把所有视频回传到一个中心。

### 5.5 成本优势的来源总结

1. 减少重复推理硬件；
2. 提高算力利用率；
3. 减少模型、依赖和规则副本；
4. 减少部署、升级、备份和排障工时；
5. 降低终端采购和更换频率；
6. 通过子码流、跳帧、ROI、量化和事件存证降低带宽与存储；
7. 统一 Outbox，减少重复通知和重复审计。

## 6. 为什么集中推理更“实用”

### 6.1 对甲方：交付更像设备，而不是工程项目

甲方通常不希望为每个值班室部署一套 AI 环境。集中推理可以把交付边界定义清楚：

- 一台中心主机；
- 一套模型和规则；
- 一个统一事件库；
- 一个通知配置中心；
- 若干轻量终端。

验收、培训、备份和后续维护都围绕一个中心展开。

### 6.2 对运维：升级一次，全厂生效

模型升级、规则调整、通知通道修改、数据库备份和日志采集都只需要在中心完成。新增终端不增加模型维护工作。

### 6.3 对值守人员：操作路径更短

值守人员只关心“看画面、确认事件、标记误报、回放、通知”。集中推理把这些界面统一到一个事件库和时间线上，避免在不同终端之间切换。

### 6.4 对后续扩展：路径清晰

扩展顺序建议为：

1. 降低分析帧率和分辨率；
2. 使用 ROI 和跳帧；
3. 采用更小模型或量化模型；
4. 增加中心批处理和任务调度；
5. 升级中心 GPU；
6. 增加第二推理节点。

这条路径比“逐台更换值守电脑”更可控。

## 7. 可靠性与失效模式设计

集中推理的最大质疑是单点故障。必须在方案中主动回答，而不是回避。

| 失效模式 | 影响 | 必要措施 |
|---|---|---|
| 中心主机宕机 | 所有智能分析停止 | 看门狗、自动重启、UPS、磁盘健康检查 |
| 中心网络中断 | 终端无法查看实时事件 | 终端保留最近事件缓存；网络恢复后同步 |
| 摄像机断流 | 单路无画面 | 独立流健康状态、自动重连、告警 |
| 磁盘写满 | 事件媒体无法保存 | 容量阈值告警、媒体保留策略、自动清理 |
| 模型异常 | 误报/漏报或服务不可用 | 健康检查、模型版本回滚、降级策略 |
| 通知通道失败 | 告警未送达 | Outbox 重试、指数退避、失败审计 |
| 数据库损坏 | 事件和审计不可用 | WAL、完整性检查、定时备份、恢复演练 |

建议的交付指标（需在 PoC 中确认）：

- 中心服务连续运行 72 小时无崩溃；
- 单路视频中断后自动重连；
- 事件从触发到终端可见的端到端延迟目标小于 3 秒；
- 通知通道健康时，Outbox 最终送达率大于 99%；
- 数据库每日备份，RPO ≤ 24 小时，RTO ≤ 15 分钟；
- 关键配置变更和事件处置 100% 写入审计日志。

这些是项目目标，不是未经测试的承诺；应在验收测试中逐项记录。

## 8. 安全与合规

集中推理会形成“视频和事件集中存储”，因此安全要求比终端分散存储更高。

建议基线：

- 中心服务只监听受控内网地址，不直接暴露公网；
- 使用 HTTPS 或受控反向代理；
- 中心推理 API 使用 Bearer Token 或双向认证；
- Webhook Secret、SMTP 密码、短信 Token 只保存在运行时内存或受保护凭据存储；
- 按角色划分查看、处置、配置和导出权限；
- 所有配置变更、事件处置、导出和登录写入审计日志；
- 默认不启用人脸识别，人员轨迹和视频保留期限可配置；
- 遵循《个人信息保护法》及企业内部的视频监控管理制度；
- 参考 GB/T 28181、GB 35114、GB/T 22239、GB 50348 和 IEC 62443 的相关要求。

安全设计的目标不是“完全没有风险”，而是让风险可识别、可控制、可审计、可恢复。

## 9. 部署与验收路线

### 阶段 0：现场勘察

确认摄像机路数、编码格式、子码流能力、NVR 接入方式、交换机带宽、机柜供电和终端数量。

### 阶段 1：4～8 路 PoC

- 使用真实摄像机和真实场景；
- 记录不同模型/分辨率/帧率下的 CPU/GPU 占用；
- 统计误报、漏报和告警延迟；
- 验证 Webhook/邮件/短信通道；
- 连续运行 72 小时。

PoC 阶段建议记录以下容量基线。下表中的范围是工程规划目标，不是模型或硬件的固定承诺：

| 部署档位 | 摄像机路数 | 建议分析输入 | 目标分析帧率 | 备注 |
|---|---:|---|---:|---|
| CPU 入门 | 4～8 | 480p～720p | 1～5 FPS | 需关闭不必要的检测类别，启用 ROI |
| 单 GPU 标准 | 16～32 | 480p～720p | 2～10 FPS | 取决于模型大小、batch、显存和 GPU 型号 |
| 多节点扩展 | 32+ | 按区域分配 | 按业务优先级 | 建议按厂区或产线拆分推理节点 |

验收时至少记录：每路平均推理延迟、P95 延迟、CPU/GPU 占用、显存占用、队列积压、视频断流重连时间和通知送达时间。

### 阶段 2：生产部署

- 部署中心主机、UPS、备份目录和监控；
- 配置事件保留策略和通知通道；
- 导入厂区拓扑、摄像头和规则；
- 培训值守人员；
- 完成验收测试和运维交接。

### 阶段 3：扩容

根据实测结果决定：

- 增加摄像机；
- 降低帧率或启用 ROI；
- 升级 GPU；
- 增加推理节点；
- 或对远端厂区采用边缘-中心混合架构。

## 11. 什么时候不应该采用纯集中推理

以下情况应保留边缘推理或采用混合架构：

1. 摄像机分布在多个相距很远的厂区，视频回传成本高；
2. 现场网络不稳定，中心不可达时仍需本地告警；
3. 甲方要求视频原始帧不得离开本厂区；
4. 单路视频分辨率极高，中心带宽不足；
5. 需要毫秒级本地 PLC/设备联动；
6. 中心机房没有可靠供电、散热和运维条件。

混合架构可以采用：

```text
园区边缘节点：取流 + 轻量推理 + 本地缓存
        │
        └── 中心平台：跨厂区事件汇总、模型管理、统一通知
```

## 12. 最终结论

对 FactoryGuard 的目标市场，集中推理的核心价值不是“把算力集中起来”，而是：

- 把重复的模型、数据库、规则和通知收敛；
- 让终端变薄，降低采购和更换成本；
- 让算力共享，提高利用率；
- 让升级、备份、审计和排障只做一次；
- 让多摄像头事件和通知形成统一闭环；
- 让系统更像一台可交付的设备，而不是多个项目的拼装。

因此，建议 FactoryGuard 将**集中推理作为默认架构**，将本地推理保留为兼容模式和特定场景的降级方案，并在产品路线中逐步实现“中心直接拉取 RTSP 子码流”，进一步减少终端参与和网络重复传输。
